# 04 调度与执行

这一层是程序的核心，全部在 `app/runner.py` 的 `Engine` 里。

## 1. 时间模型

站点按自己的服务器时间开窗，手机/电脑的时钟可能差几秒。

```python
server_now()   # 校准后的「站点时间」——所有调度判断都用它
now_local()    # 本机时间（带时区），只用于算「今天」
```

**校准**（`calibrate()`）：向站点发一次 `HEAD /`，读响应头 `Date`。
`Date` 只精确到秒，所以用「请求发出时刻」与「响应收到时刻」的中点做参考，
削掉一半 RTT 的误差。校准结果 `_offset = 站点时间 − 本机时间`，每 10 分钟自动重校一次。

> 校准失败不影响主流程，只是 `offset` 保持旧值（初始为 0）。

## 2. 执行时机：`next_occurrence()`

每个任务只认一个**目标日期**（`target_date`），返回值是「下一次该执行」的站点时间戳：

```
target < 今天                → None        （任务失效，worker 退出）
target ≤ 今天 + MAX_ORDER_DAYS → max(now, 上次失败后的重试时刻)
target > 今天 + MAX_ORDER_DAYS → 窗口开启日（target − 7 天）的 open_time
```

用一张表看得更直接（`MAX_ORDER_DAYS = 7`，今天是 10-20）：

| 目标日期 | 下次执行 |
| --- | --- |
| 10-19 | 不执行（已过去） |
| 10-20 ~ 10-27 | 立刻（若上次失败，等 `RETRY_SECONDS`） |
| 10-30 | 10-23 00:00:30（`open_time`） |

`open_time` 默认 `00:00:30`，只对「还没进窗口」的任务有意义；
日期已经在窗口内时直接执行，忽略这一项。

## 3. worker 的生命周期

```
sync_workers()
   └─ 每个启用任务一个 asyncio.Task（_workers[task_id]）
        循环：
          读取任务 → next_occurrence()
          睡到 planned − prewarm（默认提前 8 秒，先做一次校时）
          执行 _execute()
          再回到循环
```

三个防重复/防抖机制：

| 机制 | 作用 |
| --- | --- |
| `_versions[task_id]` | 任务被修改后 `refresh_task()` 递增版本，旧 worker 发现版本不符就退出 |
| `_locks[task_id]` | 同一任务串行执行；手动「立即执行」撞上定时任务时直接跳过，不排队 |
| `_next_try[task_id]` | 记录失败后的重试时刻，避免「窗口内反复立刻重跑」把 CPU 打满 |

> 这条曾经踩过坑：如果某次执行结束后**不安排下一次**，窗口内会变成忙循环，
> 事件循环被占死，页面全部卡住。所以 `finally` 里对**每一种**结果都排了下次。

## 4. 一次执行的完整时序

`_execute(task, planned, trigger)`，`trigger` 取 `schedule` / `manual` / `now`：

```
① build_ctx()                任务 → 日期/时段/人数/场地 等占位符
② [可选] 查询模板             拿余量或附加字段；失败不影响下单
③ candidates_from_task()     按勾选顺序生成候选场地（白名单，绝不越界）
④ ensure_token()             令牌将过期则换新，换完立刻校验
⑤ 令牌过期且换不了 → 直接中止，不发任何请求
⑥ 演练模式？ → 记录「将依次尝试 N 个场地」，按成功收尾（不 POST）
⑦ 下单循环
       for 轮次 in 1..max_attempts:
           for 场地 in 候选:
               _call(order_template) → _judge()
               成功 → 停，记录「第 N 轮提交成功：场地X」
               失败 → 记录 HTTP 状态与提示，换下一块
           超过 MAX_RUN_SECONDS(120s) → 停止
⑧ finally：finish_run() 落库 + 安排下一次
```

每一步都会写进 `attempts` 表（URL、请求头、请求体、状态码、响应片段），
所以事后能在「记录」里逐条回放。

## 5. 成功判定

`_judge()` 按顺序判断，任一不满足即失败：

1. 响应 JSON 里 `name` 以 `blink\` 开头 → 视为框架级错误（即使 2xx）；
2. 响应体既不是 JSON 也不是 HTML（纯文本报错）→ 失败；
3. `success_mode == "expr"` → 用 `jmespath` 表达式判断；
4. 否则 `200 ≤ status < 300` 即成功。

默认就是第 4 条：站点提交成功返回 200/201，冲突返回 409。

## 6. 重试与收尾

`finally` 里的规则：

| 结果 | 动作 |
| --- | --- |
| 成功，且不是演练 | 停用任务（目标日期只有一天，不必重复预约） |
| 失败 / 演练 | `_next_try = now + RETRY_SECONDS`（默认 600 秒） |

重试不会无限进行：目标日期一过，`next_occurrence()` 返回 `None`，worker 自然退出。

## 7. 令牌续期

### 7.1 两条通道

| 通道 | 请求 | 前提 |
| --- | --- | --- |
| passport 会话 Cookie（优先） | `POST https://passport.seiue.com/authorize`，表单 `response_type=token&client_id=<web id>` | 有 `passport` 域的会话 Cookie |
| refresh_token（兜底） | `POST https://api.seiue.com/chalk/oauth/tokens`，表单 `grant_type=refresh_token&...` | 数据库里存过 RT（界面已不提供入口） |

站点 Web 端自己走的是第一条：它不保存 RT，令牌将过期时用 `withCredentials` 带上
passport 域的 HttpOnly Cookie 换新。所以填了 Cookie 就不需要别的了。

### 7.2 三个触发点

| 时机 | 说明 |
| --- | --- |
| 启动时 | `Engine.start()` 里调一次 `ensure_token()` |
| 后台巡检 | `_token_keeper` 每 `TOKEN_CHECK_SECONDS`（300s）检查一次 |
| 每次执行前 | `_execute` 里调一次，确保下单时令牌可用 |

判断依据是 JWT 的 `exp`：剩余不足 `TOKEN_REFRESH_SKEW`（600 秒）就换。

### 7.3 换完必须校验

```
mint()/exchange() 成功
   → 用新令牌 GET 一次场地清单
        2xx  → 落盘（同时回写可能被轮换的 Cookie / RT）
        其它 → 丢弃新令牌，保留旧的，并在界面报告原因
```

这一步很关键：宁可继续用旧令牌，也不要把一个坏令牌写进去——
否则一次失败就会让后续所有执行都 401。

## 8. 自愈与可观测性

| 机制 | 位置 | 行为 |
| --- | --- | --- |
| 事件循环探针 | `main._loop_monitor` | 每 2 秒测一次漂移，>5 秒打印所有线程栈到日志 |
| 看门狗 | `ctl.sh watchdog`（模块） | 进程在但 `/healthz` 连续 3 次不通 → 自动重启 |
| 状态心跳 | `service.sh` | 每 20 秒写 `status.json`，供模块控制台直接读取 |
| 执行留痕 | `runs` / `attempts` | 每次请求的完整报文都在数据库里 |

## 9. 并发模型

- 单进程、单事件循环；
- 所有网络请求 `await`，不阻塞；
- 数据库操作是同步的，但每次只做几条小语句（毫秒级）；
- 同一任务串行（`_locks`），不同任务之间可以并行等待各自的时刻。

因此一台普通手机跑十几个任务没有压力，瓶颈在网络与站点响应。
