# 01 架构总览

## 1. 这个程序解决什么问题

校园场馆系统只提供一个网页：登录后手动选场地、选时段、点提交，可预约窗口只有未来 7 天。
热门时段在窗口开启的瞬间被抢完，人工操作几乎抢不到。

程序把这件事拆成两半：

- **配置一次**：把「我要哪个日期、哪个时段、哪几块场地」存成任务；
- **自动执行**：到了能约的时候，按配置直接发请求，并记录每一次请求与响应。

## 2. 分层结构

```
┌──────────────────────────────────────────────────────────────┐
│  展示层                                                       │
│    app/views/*.html          网页界面（服务端渲染，无前端框架） │
│    kernelsu-module/webroot   模块控制台（状态/启停/内嵌界面）    │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTP（127.0.0.1:8080）
┌───────────────────────────▼──────────────────────────────────┐
│  Web 层    main.py                                            │
│            路由、表单解析、重定向、登录口令、页面上下文           │
│            webcore.py —— 基于 Starlette 的极薄内核              │
└───────────────────────────┬──────────────────────────────────┘
                            │ 调用领域函数
┌───────────────────────────▼──────────────────────────────────┐
│  领域层                                                       │
│    render.py     任务 → 占位符上下文 / 模板渲染 / 响应取值       │
│    preset.py     预置模板、cURL → 占位符化模板                  │
│    curlparse.py  解析「Copy as cURL」                          │
│    tokeninfo.py  解析 JWT 的 exp                               │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│  执行层    runner.py（Engine）                                 │
│            时钟校准 · 定时唤醒 · 下单 · 判定 · 重试 · 令牌续期    │
│            crypto.py / oauth.py / passport.py —— 凭据与续期     │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│  存储层    store.py（SQLite，单文件，WAL）                      │
│            settings / templates / tasks / runs / attempts      │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTPS
┌───────────────────────────▼──────────────────────────────────┐
│  外部系统                                                     │
│    api.seiue.com        场地清单 / 提交预约 / 我的预约          │
│    passport.seiue.com   会话 Cookie → 换新令牌                 │
└──────────────────────────────────────────────────────────────┘
```

**没有**：消息队列、缓存服务、定时任务框架、前端构建链、容器。整份程序是一个 Python 进程。

## 3. 两条主线

### 3.1 配置流（人只做一次）

```
浏览器复制 cURL
      │
      ▼
curlparse.parse()            拆成 method / url / headers / body
      │
      ▼
preset.build_order_template() 场地 ID → {{venue_order_id}}
                              time_ranges / date_ranges / capacity … → 占位符
      │
      ▼
store.save_template(kind=order)
      │
      ▼
任务表单：目标日期 + 时段 + 勾选场地 + 人数
      │
      ▼
store.save_task()  →  Engine.refresh_task()  →  起一个 worker
```

### 3.2 执行流（程序自己做）

```
worker 循环
  │  取任务 → next_occurrence() 算下次时刻
  │  睡到那个时刻（按站点时间）
  ▼
_execute()
  ├─ build_ctx()            任务 → date/time_ranges/capacity/venue_order_id
  ├─ [可选] 查询模板        拿余量、附加字段
  ├─ candidates_from_task() 按勾选顺序生成候选场地
  ├─ ensure_token()         快过期就换新，换完校验
  ├─ 演练？→ 直接记成功返回
  └─ 下单循环
        轮次 × 候选场地 → _call() → _judge() → 成功即停
  ▼
finish_run()  写 runs + attempts
  ├─ 真约到 → 停用任务
  └─ 没约到 → RETRY_SECONDS 后再来
```

## 4. 模块职责

| 文件 | 职责 | 关键约束 |
| --- | --- | --- |
| `config.py` | 环境变量、站点地址、窗口天数、续期阈值 | 不出现硬编码路径 |
| `store.py` | 所有数据库读写、建表与轻量迁移 | 每次操作独立连接，用完关闭 |
| `render.py` | 占位符上下文与类型感知替换 | 日期只认 `target_date` |
| `curlparse.py` | cURL 文本 → 结构化请求 | 只解析，不做业务假设 |
| `preset.py` | 预置场地清单模板、cURL 模板化 | 不预置下单模板（必须来自真实请求） |
| `tokeninfo.py` | JWT `exp` 解析 | 只解码不验签，用于展示与告警 |
| `crypto.py` | 会话凭据加密（HMAC-CTR + EtM） | 只用标准库，密钥格式与旧版兼容 |
| `oauth.py` | `refresh_token` 换新令牌 | 表单编码，错误信息剥成一句人话 |
| `passport.py` | 会话 Cookie 免密换新令牌 | 兼容多种粘贴形态，处理 Cookie 轮换 |
| `webcore.py` | 路由、参数注入、模板、静态文件、中间件 | 保持与 FastAPI 相同写法 |
| `main.py` | 页面、表单、重定向、鉴权、生命周期 | handler 一律返回 Response |
| `runner.py` | 调度与执行、令牌巡检、时钟校准 | 单任务串行，成功后自动停用 |
| `run.py` | 本地启动器 | 自动探测局域网地址、端口占用 |

## 5. 关键取舍

**为什么不用 FastAPI**
FastAPI 的校验层依赖 pydantic v2，核心是 Rust 扩展。Termux（Android / bionic libc）上
PyPI 的 manylinux wheel 全部不可用，安装时必须现场装 Rust 工具链。项目实际只用到
路由、参数注入、模板、静态文件这几样能力，而它们全部来自 Starlette（FastAPI 的底座），
于是 `webcore.py` 用 Starlette 复刻了同名同形的写法，`main.py` 一个字都不用改。

**为什么加密自己实现**
`cryptography` 同样是 Rust + OpenSSL 扩展。`crypto.py` 用 `hmac` / `hashlib` / `os.urandom`
实现 HMAC 派生密钥流 + Encrypt-then-MAC，安全性等同 AES-CTR + HMAC，
密钥格式与旧版 Fernet 完全一致，升级不用迁移。

**为什么用「模板 + 占位符」而不是写死接口**
站点字段名、身份请求头、下单类型都会变。模板把所有可变部分抽成占位符，
换站点/换字段只改模板不改代码；「一键导入」还能把真实请求直接变成模板。

**为什么没有「先查余量再抢」**
实测站点没有「某场地某时段是否可约」的接口（试过 `GET …/orders` 返回 405，其余猜测路径 404）。
所以策略是：按任务里的场地顺序直接提交，冲突就换下一块，再不行进入重试。

**为什么调度用站点时间**
手机与站点服务器可能差几秒，而窗口是按服务器时间开的。`calibrate()` 读响应头 `Date`
算出偏移，`server_now()` 之后一律用校准时间做判断。

**为什么模块控制台有两条通道**
KernelSU 的 WebUI 通过 `ksu.exec` 执行 root 命令，但各分支的桥接签名不一致，
一旦不兼容就完全读不到状态。所以状态优先走「模块写好的 `status.json` + fetch」，
命令通道只用于启停；两条任意一条通，页面就能用。

## 6. 代码地图（建议阅读顺序）

```
config.py → store.py → render.py → runner.py → main.py
```

1. `config.py`：先知道有哪些开关和地址；
2. `store.py`：五张表决定了整个数据模型；
3. `render.py`：理解占位符，才能看懂模板与任务；
4. `runner.py`：核心逻辑都在这里（调度 + 执行 + 续期）；
5. `main.py`：只是把这些能力暴露成页面和表单。

其余文件都是外围：`curlparse` / `preset` 负责接入，`crypto` / `oauth` / `passport` 负责凭据，
`tokeninfo` 负责展示，`webcore` 负责 HTTP。

## 7. 状态与数据的边界

| 存在哪 | 内容 | 丢了会怎样 |
| --- | --- | --- |
| `data/app.db` | 模板、任务、执行记录、设置 | 全部配置丢失，需重新导入 cURL |
| `data/secret.key` | 加密密钥 | 已保存的会话与 Cookie 解不开，需重新粘贴 |
| `/data/adb/badminton-booker/`（模块） | 日志、pid、状态快照 | 无影响，重启重建 |

`app.db` 与 `secret.key` **必须一起备份**，缺一不可。
