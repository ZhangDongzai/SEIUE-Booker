# 02 架构设计

## 1. 架构总览

单进程、无外部中间件。同一个 ASGI 应用同时承担「网页界面」与「后台调度」，二者共享同一事件循环，SQLite 作为唯一状态存储。

运行形态只有一种：在主机上直接跑一个 Python 进程（`python run.py`）。
不依赖容器、反向代理或外部服务，Termux 等移动端也是同一份代码——见 [07 Termux 部署](07-Termux%20部署.md)。

## 2. 模块职责

| 模块 | 职责 | 关键点 |
| --- | --- | --- |
| `config.py` | 读取环境变量、路径、时区、超时、代理 | 所有可变项集中于此，无硬编码路径 |
| `crypto.py` | 会话加密（标准库 HMAC-CTR + EtM）、掩码 | 密钥首次启动自动生成于 `/data/secret.key`（0600） |
| `curlparse.py` | cURL / 头部文本 → `{method,url,headers,body}` | 用 `shlex` 分词，忽略伪头，兼容 `\` 续行 |
| `tokeninfo.py` | 解 Bearer JWT 的 `exp`，判断过期/即将过期 | 不解签、不校验签名，只用于展示与提前拦截 |
| `oauth.py` | 用 refresh_token 换新令牌（`POST /chalk/oauth/tokens`，表单编码） | 只做 HTTP；成功/失败都以 `RefreshError` 归口，换到新令牌先校验再落盘 |
| `preset.py` | 预置场地清单模板（不预置下单模板）；把 cURL 转成占位符化模板 | URL 里场地 ID、请求体 5 字段自动替换 |
| `store.py` | SQLite 建表、CRUD、统计、场地清单缓存 | WAL 模式，每次操作独立连接；启动时自动补列升级 |
| `render.py` | 构造上下文（含 `date_ranges`/`time_ranges`）、渲染 URL/头/体、JMESPath 提取 | 数字类型感知替换；裸 JSON 注入 |
| `runner.py` | 时钟校准、任务协程、执行编排、记录落库 | 身份头以会话为准；令牌过期直接拦截 |
| `webcore.py` | 极薄 Web 内核：路由、参数注入、中间件、静态文件 | 基于 Starlette；保持与 FastAPI 相同的写法 |
| `main.py` | 路由、鉴权中间件、生命周期 | lifespan 内建表、预置模板、启动/停止 Engine |

## 3. 数据模型

```sql
settings(key TEXT PRIMARY KEY, value TEXT)  -- session_headers(加密)、venues_cache、check_url 等
templates(id, name, kind['list'|'order'], method, url, headers JSON, body, note, created_at, updated_at)
tasks(
  id, name, enabled,
  target_date,          -- 目标日期（YYYY-MM-DD），调度唯一依据
  open_time,            -- 窗口开启日的触发时刻
  venues,                       -- 场地名（由 ID 自动推导，仅展示）
  venue_ids,                    -- 逗号分隔的场地 ID，**顺序即优先级，也是白名单**
  slot_start, slot_end, split_minutes,   -- 0=整段，>0=按粒度拆分
  order_type, capacity, description,
  list_template_id, order_template_id,
  map_items, map_venue_name, map_venue_id, map_venue_num,   -- 旧版字段映射，v1.1 起不再使用，保留列以兼容老库
  map_slot_start, map_slot_end, map_slot_id, map_available, map_available_true,
  extras JSON,                  -- [{"name":"csrf","expr":"data.token"}] 从清单响应提取变量
  success_mode['http2xx'|'expr'], success_expr,
  max_attempts, interval_ms, prewarm_ms, dry_run,
  created_at, updated_at
)
runs(id, task_id, trigger['schedule'|'manual'], planned_at, started_at, finished_at,
     status['running'|'success'|'failed'|'skipped'], message, resolved JSON)
attempts(id, run_id, seq, venue_name, method, url, request_headers, request_body,
         http_status, duration_ms, ok, response_excerpt, error)
```

关系：`tasks` 1—N `runs` 1—N `attempts`；`templates` 被 `tasks` 以可空外键引用（模板删除时置空，任务保留并在界面上标红提示）。

升级策略：`init_db()` 后用 `PRAGMA table_info(tasks)` 比对，缺列则 `ALTER TABLE ADD COLUMN`，
老库（v1.0）可直接升级、数据不丢。

## 4. 执行时序

```
Engine.start()
  ├─ 校准时钟：GET 站点根路径 → 解析 Date 头 → offset = server - local
  └─ 为每个 enabled 任务 spawn 一个协程

TaskWorker 循环:
  planned = next_occurrence(task)              # 窗口内=立刻；未进窗口=窗口开启日 00:00:30
  sleep_until(planned - prewarm)               # 分段睡眠，最多 30s 一片，便于热更新
  ├─ run#1 创建 (status=running)
  ├─ 生成候选：任务里勾选的场地 ID（白名单），可选再用清单模板补 need_approval
  ├─ 令牌检查：exp 已过 → run=failed 并提示重新导入（不发任何请求）
  ├─ sleep_until(planned - 200ms)
  ├─ 到点：按场地顺序 ↓
  │    ┌─ 渲染下单模板（venue_order_id + date_ranges + time_ranges…）→ 发送 → 记录 attempt
  │    ├─ 判定成功（2xx 且非 blink 异常）→ 立即 break，run=success
  │    └─ 失败 → 下一块场地
  ├─ 全部失败 → 等待 interval_ms → 下一轮（≤ max_attempts）
  └─ 收尾：写 finished_at / status / message；回到循环开头
```

`dry_run=1` 时只列候选、不提交，用于验证配置（不发任何 POST）。

## 5. 时间精度策略

1. **时钟基准**：`offset = 站点 Date 头 - 本机时间`，调度时把「站点时间戳」换算为「本机应触发的时刻」：`target_local = target_server - offset`。每 10 分钟重校准一次，失败时沿用旧值并记日志。
2. **分段睡眠**：剩余 > 30s 时按 30s 睡眠（便于任务热更新、系统休眠恢复后重算）；30s~50ms 之间用 `asyncio.sleep(remain - 0.03)`；最后 30ms 用 1ms 粒度轮询。
3. **预热**：`prewarm_ms` 内完成 TCP/TLS 握手与列表查询，避免到点时才建连（TLS 握手往往耗时 100~300ms）。
4. **提前量**：到点前 200ms 结束睡眠，给事件循环调度留出余量；实际发出时间每次落库（`started_at`），可回看偏差。
5. **限制**：精度上限受本机到站点的网络 RTT 与站点网关排队影响，本项目只能保证「发出时刻」准确，无法保证「服务端处理时刻」。

## 6. 关键设计取舍

| 决策 | 选择 | 理由 | 代价 |
| --- | --- | --- | --- |
| 对接方式 | 纯 HTTP 重放（非浏览器自动化） | 毫秒级、资源小、可在 NAS 长期运行 | 接口变更需改配置；需用户抓包 |
| 接口定义 | 全部外置为模板 | 未知接口的唯一诚实做法 | 首次配置有学习成本 |
| 匹配策略 | 「列表解析出 ID」而非「猜 ID」 | 真实系统多用场地/时段 ID 下单 | 依赖列表接口可用 |
| 存储 | SQLite | 单用户、低并发、零运维 | 不适合多实例水平扩展 |
| 调度 | 自研协程（不用 APScheduler） | 需要 30ms 级对齐与热更新 | 代码量略增，无 cron 表达式 |
| 重试 | 串行 + 候选轮换 | 避免重复下单与风控触发 | 极端并发下不如并行抢 |
| 鉴权 | 可选单口令 | 内网部署为主，不引入用户体系 | 无多用户/权限分级 |

## 7. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 会话过期（SSO 失效） | 所有请求 401/302 | 自检按钮 + 执行记录里识别 401/302 并给出「会话可能失效」提示 |
| 接口字段变更 | 下单失败 | 模板 + 字段映射可改，无需改代码；记录里保留原始响应便于定位 |
| CSRF / 一次性 token | 403 | 请求头支持占位符，可把 token 从列表响应提取后注入 |
| 站点风控/限频 | IP 临时封禁 | 默认请求间隔 ≥300ms、单任务串行、总时限 120s；不建议调低间隔 |
| 本机时钟漂移 | 抢点晚到 | 站点 Date 头校准 + 记录偏差 |
| 主机休眠/断网 | 错过窗口开启时刻 | 文档要求关闭休眠、用 systemd `Restart=always` 常驻、建议接入 UPS |
| 重复预约 | 账号违约 | 成功即停 + 任务互斥 + 建议预约成功后停用任务 |

## 8. 部署拓扑

```
主机（Linux / NAS / Android·Termux，x86_64 或 arm64 均可）
└── 进程：python run.py  (TZ=Asia/Shanghai)
    ├── :8080      内网访问（APP_HOST=0.0.0.0）
    └── ./data/    app.db（SQLite）+ secret.key（需一起备份）
```

服务化：Linux 用 systemd（`Restart=always` 替代容器的自动重启），
Termux 用 `termux-wake-lock` + 关闭电池优化，详见 [03 依赖与部署](03-依赖与部署.md)、
[07 Termux 部署](07-Termux%20部署.md)。

无入站外网依赖；出站仅需 `chalk-c3.seiue.com:443` 与 `passport.seiue.com:443`。
不加反向代理即可用；如需 HTTPS，用 Nginx / Caddy 反代到 `http://127.0.0.1:8080`。

## 9. 扩展点（本次不实现）

- 通知渠道（邮件 / 企业微信机器人）：`runner.py` 的 `finish_run()` 里预留了钩子位，加一个 `notify.py` 即可。
- 多账号：把 `session_headers` 从 `settings` 提升为 `accounts` 表，`tasks.account_id` 引用即可。
- 多实例：SQLite 换成 PostgreSQL，调度加分布式锁。
