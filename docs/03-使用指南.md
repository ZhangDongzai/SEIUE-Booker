# 03 使用指南

## 1. 首次配置（四步）

### 第一步：导入一条真实的下单请求

1. 电脑浏览器打开场馆预约页，登录；
2. F12 → **网络（Network）** → 手动提交一次预约（可以故意选一个已满的时段）；
3. 找到那条 **POST** 请求（形如 `.../order-venues/2953/orders`），右键 → **Copy as cURL (bash)**；
4. 网页里打开「设置 → 一键导入」，粘贴、提交。

程序会：

- 从 cURL 的 `authorization: Bearer …` 里取出令牌；
- 把 URL 里的场地 ID 换成 `{{venue_order_id}}`；
- 把请求体里的时段、日期、人数、类型换成占位符；
- 生成一份 `下单模板`，并顺手同步一次场地清单。

> 别复制 OPTIONS 那条——那是浏览器的预检请求，程序会直接拒绝并提示。

### 第二步：配置会话 Cookie（强烈建议）

令牌 24 小时过期。填一次会话 Cookie 就能长期自动续期，不用每天重贴 cURL。

1. F12 → **Application → Cookies → `https://passport.seiue.com`**；
2. 把该域下的 `Name=Value` 整段复制（通常一两条，形如 `PHPSESSID=xxxx`）；
3. 粘到「设置 → 会话 Cookie」→ 保存。

保存后程序会连续做三件事，并合并成一条提示：

```
会话 Cookie 已保存；已换到新令牌；已同步 6 个场地；会话自检通过（HTTP 200）
```

任何一步失败都会写清是哪一步、什么原因。

### 第三步：建一个任务

「任务 → 新建」：

| 字段 | 说明 |
| --- | --- |
| 预约日期 | 具体某一天。窗口内（今天起 7 天）保存后立即执行；更远的日期等到窗口开启那天 |
| 时段 | 开始/结束，如 `17:30` – `18:30`，整段提交 |
| 场地 | 从同步下来的清单里勾选，**勾选顺序就是尝试顺序** |
| 人数 | 对应接口的 `capacity` |
| 模板 | 会自动选中已有的那一个；没有下单模板时页面会提示先去导入 |
| 演练模式 | 只走流程、不提交，用来验证场地与时间对不对 |
| 窗口开启时刻 | 仅对「还没进窗口」的任务生效，默认 `00:00:30` |
| 启用 | 取消勾选则保存但不排程 |

任务名由「日期 + 时段」自动生成（如 `2026-10-21 17:30-18:00`），不需要填。

### 第四步：先演练，再转正

1. 勾上「演练模式」保存 → 程序立刻跑一轮，记录里会写「演练模式：将依次尝试 N 个场地」；
2. 到「记录」里核对：日期、时段、场地列表是否都正确；
3. 回任务取消演练、保存。日期在窗口内会立即执行。

## 2. 页面地图

| 页面 | 路径 | 作用 |
| --- | --- | --- |
| 仪表盘 | `/` | 令牌状态、任务概览、最近执行 |
| 任务 | `/tasks` | 列表、启停、立即执行、删除 |
| 新建/编辑任务 | `/tasks/new`、`/tasks/{id}/edit` | 日期、时段、场地、模板 |
| 模板库 | `/templates` | 查询/下单模板，可解析 cURL、可试发 |
| 记录 | `/runs`、`/runs/{id}` | 每次执行的请求与响应明细 |
| 设置 | `/settings` | 导入会话、会话 Cookie、同步场地、自检、校时 |

## 3. 令牌与会话

程序支持两种携带凭据的方式，导入哪个用哪个：

| 方式 | 来源 | 有效期 | 续期 |
| --- | --- | --- | --- |
| Bearer 令牌 | cURL 的 `authorization` 头 | 24 小时 | 需配会话 Cookie 才能自动续 |
| Cookie 会话 | 带 `cookie:` 的 cURL | 看服务端 | 无需续期（但站点不允许跨域带 Cookie，通常不可用） |

「设置」页顶部会显示令牌剩余时间：

- **有效**：绿色，标注剩余时长；
- **已过期**：红色，此时执行会被直接拦下，不会发出无效请求。

## 4. 任务字段详解

### 4.1 执行时机

任务只认一个「预约日期」，规则很简单：

| 目标日期 | 行为 |
| --- | --- |
| 早于今天 | 任务失效，不再执行 |
| 今天 ~ 今天+7 天 | 保存后**立即执行**；失败按 `RETRY_SECONDS`（默认 10 分钟）重试 |
| 晚于今天+7 天 | 等到「目标日期 − 7 天」那天的 `窗口开启时刻` 开始执行 |

约到之后任务**自动停用**（目标日期只有一天，不必重复预约）。

### 4.2 场地顺序

勾选多个场地时，按**勾选的先后顺序**依次提交，某一块冲突就换下一块。
站点没有「余量查询」接口，所以程序是「直接提交 + 失败换场地」。

### 4.3 重试

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| 轮次（`max_attempts`） | 5 | 一次执行内最多提交几轮 |
| 间隔（`interval_ms`） | 300ms | 轮次之间的间隔 |
| 单轮时限 | 120s | 超过就停止，避免无限重试 |

## 5. 模板与占位符

模板就是「一条请求」：方法、URL、请求头、请求体，其中可变部分写成 `{{name}}`。

```
POST https://api.seiue.com/scms/venue/order-venues/{{venue_order_id}}/orders
Content-Type: application/json

{"type":"{{order_type}}","time_ranges":{{time_ranges}},
 "date_ranges":{{date_ranges}},"capacity":"{{capacity}}","description":"{{description}}"}
```

注意两处容易踩的坑：

- `{{time_ranges}}` / `{{date_ranges}}` 要**裸写**（前后不要加引号），它们输出 JSON 数组/对象；
- `"{{capacity}}"` 这种写法也会输出**数字**（`2` 而不是 `"2"`），因为替换是类型感知的。

完整占位符清单见 [05 数据与接口 §2](05-数据与接口.md)。

## 6. 记录怎么看

「记录」列表按开始时间倒序。点进去是这次执行的明细：

```
状态：成功 / 失败 / 运行中
信息：第 1 轮提交成功：羽毛球场地12号（该场地需要审批，请到「我的预约」确认状态）
```

下面按顺序列出每一个 HTTP 请求：场地、方法、URL、状态码、耗时、请求头、请求体、响应片段。
排查失败原因时看最后几条即可——通常是 `HTTP 409`（冲突）、`401`（令牌失效）。

## 7. 常见提示对照

| 提示 | 含义 | 处理 |
| --- | --- | --- |
| 尚未导入会话 | 没有令牌也没有 Cookie | 设置页导入 cURL |
| Bearer 令牌已过期 | 超过 24 小时 | 重贴 cURL，或配会话 Cookie |
| 未绑定下单模板 | 任务没选模板 | 设置页一键导入，再回任务选择 |
| 任务里还没有勾选场地 | 场地为空 | 编辑任务勾选场地 |
| 第 N 轮未成功：HTTP 409 | 该场地该时段已被占 | 正常，程序会自动换下一块 |
| 该场地需要审批 | 提交成功但待审批 | 到「我的预约」确认，程序不代审批 |
