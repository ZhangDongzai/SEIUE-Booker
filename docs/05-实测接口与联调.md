# 05 实测接口与联调

本文档记录对 `chalk-c3.seiue.com` / `api.seiue.com` 的**实测结论**（2026-10-17），
以及程序据此做的取舍。文档中的字段与状态码都来自真实请求，不是推测。

## 1. 结论速览

| 项 | 结论 |
| --- | --- |
| 数据面域名 | `https://api.seiue.com`（`chalk-c3.seiue.com` 只是前端壳） |
| 场地清单 | `GET /scms/venue/order-venues` → 200，返回全部 14 个场地 |
| 场地详情 | `GET /scms/venue/order-venues/{id}` → 200 |
| 提交预约 | `POST /scms/venue/order-venues/{id}/orders` → 200 |
| 鉴权 | `Authorization: Bearer <JWT>`，缺省 → **401 Unauthorised** |
| 令牌有效期 | **24 小时**（`exp - iat = 86400`） |
| 羽毛球场地 | 6 块：`2948`–`2953`（8 号 – 13 号） |
| 预约窗口 | `max_order_days = 7`、`enable_max_order_days = true` |
| 审批 | 6 块场地全部 `need_approval = true` |
| 单人限额 | `time_limit = 1`、`time_limit_enable = true` |
| 开放时段 | 工作日 `16:35–18:30`（`open_time_ranges`，`week_days` 1–5） |
| 时段可用性接口 | **未找到**：`GET …/orders` 为 405，猜测路径均为 404 |

## 2. 鉴权

真实请求头（与浏览器一致）：

```
authorization: Bearer eyJhbGciOiJSUzI1NiIs...
x-reflection-id: 4205528
x-role: student
x-school-id: 282
origin: https://chalk-c3.seiue.com
referer: https://chalk-c3.seiue.com/
```

JWT payload 实测样例：

```json
{
  "aud": "3", "exp": 1792314620, "iat": 1792228220,
  "iss": "https://mdp.seiue.com/seiue", "sub": "4924846",
  "ctx": "provider=tencent_campus&sso=1", "sid": 13332884
}
```

要点：

- 有效期 24 小时，**这就是本程序唯一必须每天维护的一件事**。
- 程序不解签、不校验签名，只 base64 解 payload 取 `exp` 用于展示与提前拦截。
- `x-school-id` 与 `x-reflection-id` 是与账号绑定的上下文头，缺了会被判越权（`403 该操作超出了权限范围`），
  所以「一键导入」会把它们一起存进会话。

## 3. 场地清单

`GET /scms/venue/order-venues` 返回数组，单条样例（已裁剪）：

```json
{
  "id": 2953, "name": "羽毛球场地13号", "school_id": 282,
  "max_order_days": 7, "enable_max_order_days": true,
  "need_approval": true, "open_status": "opened",
  "time_limit": 1, "time_limit_enable": true,
  "scope_ids": [307473, 307474, 307475],
  "open_time_ranges": [
    {"ranges": [{"start_at": "16:35", "end_at": "18:30"}], "week_days": [1,2,3,4,5]}
  ]
}
```

用途：

- 界面里生成场地勾选列表（不用记 ID）。
- 拿到 `need_approval`，在成功消息里提示「该场地需要审批」。
- `type_id`（195756）在羽毛球场地与琴房之间是**共用**的，不能用来过滤，程序按 ID 白名单提交。

> 注意：清单里没有「这天哪些时段空着」的信息。程序**不会**从清单里自行挑场地——
> 提交对象只由你在任务里勾选/填写的 ID 决定（白名单），避免误约到琴房之类的其他场地。

## 4. 提交预约

请求（真实抓包）：

```
POST https://api.seiue.com/scms/venue/order-venues/2953/orders
content-type: application/json

{
  "type": "single_day",
  "time_ranges": [{"start_at": "2026-10-23 17:30:00", "end_at": "2026-10-23 17:45:00"}],
  "date_ranges": {"start_at": "2026-10-23", "end_at": "2026-10-23"},
  "capacity": 2,
  "description": "打球"
}
```

字段含义与程序映射：

| 字段 | 含义 | 程序来源 |
| --- | --- | --- |
| `type` | 下单类型，实测固定 `single_day` | 程序固定输出，界面不暴露 |
| `time_ranges[]` | 时段数组，元素为 `YYYY-MM-DD HH:MM:SS` 字符串 | 由「日期 + 时段起止」整段生成 |
| `date_ranges` | 日期区间（单日则起止相同） | 由任务的「预约日期」直接得出 |
| `capacity` | 使用人数（数字） | 任务字段「使用人数」 |
| `description` | 备注 | 任务字段「预约备注」 |
| 路径里的 `2953` | 场地 ID | 当前候选场地的 ID |

注意：

- `capacity` 必须是**数字**，写成字符串会被拒。模板里写 `"capacity": "{{capacity}}"`，
  渲染时按变量类型输出 `2`（不带引号）——这是本项目最关键的渲染特性。
- `time_ranges` / `date_ranges` 必须是**对象/数组字面量**，所以模板里裸写 `{{time_ranges}}`（不加引号）。
- ~~抓包里 `17:30–17:45` 只是当时的实测样例（15 分钟）。~~

> **已验证（2026-10-17 真实下单）**：提交 `2026-10-19 17:45–18:15`（30 分钟、单段）被接受，
> 服务端回算 `duration: 30`。**结论：任意起止都可以，不需要拆 15 分钟多段**，
> 程序按整段提交（拆分能力已从界面移除）。

### 4.1 成功响应与读回

提交成功的响应体就是订单实体本身（HTTP 200）：

```json
{"id":60982,"approval_status":"initiated","duration":30,"capacity":2,
 "date_ranges":{"start_at":"2026-10-19","end_at":"2026-10-19"},
 "time_ranges":[{"start_at":"2026-10-19 17:45:00","end_at":"2026-10-19 18:15:00"}],
 "venue_id":2952,"initiator_id":4205528,"created_at":"2026-10-17 19:10:11"}
```

可用的读回接口：

| 请求 | 结果 |
| --- | --- |
| `GET /scms/venue/orders/{id}` | 200，返回单个订单 |
| `GET /scms/venue/my-orders` | 200，返回本人订单数组 |
| `GET /scms/venue/orders?venue_id=2952` | 403「该操作超出了权限范围」（不能当列表用） |

`approval_status` 取值口语对照：`initiated` = 已提交待审批；null = 无审批要求。

## 5. 为什么没有「查可用时段」这一步

尝试过的路径与结果：

| 请求 | 结果 |
| --- | --- |
| `GET …/2953/orders` | `405 MethodNotAllowedException`（只允许 POST） |
| `GET …/2953/sessions` | 404 |
| `GET …/2953/order-sessions` | 404 |
| `GET …/2953/available-sessions` | 404 |
| `GET /scms/venue/orders` | `403 该操作超出了权限范围` |

也就是说：**没有公开的时段查询接口**（或权限不在学生角色）。因此本程序不假装能「先查再抢」，
而是采取「按配置直接提交 + 失败重试 + 换场地」的策略：

1. 到点前预热连接、对齐时钟；
2. 按勾选顺序对每块场地发一次下单；
3. 2xx 即停；非 2xx 立即换下一块；
4. 全部失败则等 `interval_ms` 后进入下一轮，直到 `max_attempts` 用尽。

这样即使平台没有放号时刻的公开信息，只要在放号后的一小段时间内持续尝试，也能抢到。

## 6. 审批流的影响（重要）

6 块羽毛球场地的 `need_approval` 都是 `true`，意味着：

- 程序返回 2xx 只代表**提交成功、进入审批**，不代表预约最终生效；
- 需要在校园端「我的预约」里由本人（或管理员）审批通过；
- 程序的执行记录会明确写「该场地需要审批，请到「我的预约」确认状态」，不会误报成「已预约成功」。

`approvaling_order_enable = false` 说明提交时**不要求**先有审批中的单据，直接提交即可。

## 7. 配置方式

### 7.1 一键导入（推荐）

设置页 →「① 一键导入」→ 粘贴浏览器里那条 POST cURL →「解析并生成配置」。

程序会自动：

1. 从 cURL 提取 `authorization` / `cookie` / `x-*` / `user-agent` 等存入会话（加密落盘）；
2. 把 URL 里的 `/order-venues/2953/orders` 改成 `/order-venues/{{venue_order_id}}/orders`；
3. 把请求体里的 `type` / `time_ranges` / `date_ranges` / `capacity` / `description` 改成占位符，其余字段原样保留；
4. 把 `Authorization` / `Cookie` **从模板里移除**（身份只由会话提供，换令牌不用改模板）。

生成后可直接在模板编辑页核对，通常不需要任何手工修改。

### 7.2 手动配置

模板 →「提交预约」：

```
URL     {API}/scms/venue/order-venues/{{venue_order_id}}/orders
Method  POST
Headers {"accept":"application/json, text/plain, */*","content-type":"application/json",
         "origin":"https://chalk-c3.seiue.com","referer":"https://chalk-c3.seiue.com/"}
Body    {"type":"{{order_type}}","time_ranges":{{time_ranges}},
         "date_ranges":{{date_ranges}},"capacity":"{{capacity}}","description":"{{description}}"}
```

## 8. 联调步骤

1. **导入会话**：粘贴 POST cURL → 设置页应显示「令牌剩余有效 N 小时 M 分」。
2. **同步场地**：点「同步场地」，应看到 6 块羽毛球场地，审批列显示「需审批」。
3. **建任务**：勾选 1–2 块场地，时段填 `17:30`–`18:30`（在开放时间内），人数 `2`，备注 `打球`。
4. **演练**：开启「演练模式」→ 手动执行 → 记录里只列出将尝试的场地，**没有任何 POST**。
   这一步验证的是「目标日期/时段/场地」算得对不对。
5. **真跑**：关掉演练 → 手动执行 → 详情页看请求体是否与 §4 完全一致；
   若返回 4xx，按下表处置。

## 9. 排错对照表

| 现象 | 含义 | 处置 |
| --- | --- | --- |
| `401 Unauthorised` | 令牌缺失或过期 | 设置页重新粘贴 cURL |
| `403 该操作超出了权限范围` | 缺 `x-school-id` / `x-role` 等上下文头，或该动作超出学生权限 | 用「一键导入」把上下文头一并导入 |
| `405 method is not allowed` | 用了 GET 打 `/orders` | 确认模板方法为 POST |
| `409` / 带 `message` 的业务错误 | 该时段已被占、超出开放时间、超出限额 | 换场地或换时段；详情页会显示平台原文 |
| 请求一直 `HTTP 0` | 网络不通 / 被代理拦截 | 在运行终端里 `curl -I https://api.seiue.com` 排查；如确需代理设置 `APP_PROXY` |
| 执行成功但没看到预约 | 场地需要审批 | 到「我的预约」审批 |

## 10. 每日运维

令牌 24 小时过期，建议固定节奏（例如每天上午）做一次：

1. 打开校园端 → F12 → 复制一次 POST cURL；
2. 设置页粘贴 → 解析；
3. 仪表盘确认「令牌剩余 … 小时」变绿。

若忘记更新，程序会在执行前直接判失败并提示重新导入，不会发无效请求、也不会误报成功。
